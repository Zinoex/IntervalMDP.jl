## Objective *(required)*

Resolve Finding **C-1** from `benchmark/REPORT.md` § 8 (drafted in `0g`; `0h` may have given it another id, so find it by
its title "CUDA coverage gaps"). The CUDA extension has no path for McCormick or vertex enumeration (7 fIMDP cases) or
for product processes / DFA (6 cases). The benchmark keeps these cases off CUDA through the registry
(`eltypes_cuda = DataType[]` in `benchmark/cases/fimdp.jl` and `benchmark/cases/product.jl`), so it was never measured
what a user gets when they call them with CUDA arrays.

1. **Measure first.** For one small case of each kind (McCormick, vertex enumeration, product with DFA), call `bellman`
   and `solve` with CUDA arrays (Float64 and Float32) on the merge base and record what happens: a clear error, a
   `MethodError`/scalar-indexing error, a silent fallback to the CPU (result correct but computed on the host, with
   device↔host copies), a hang, or a wrong result. Compare any returned values with the CPU result.
2. **Make the behaviour explicit, without adding GPU algorithms.** Implementing CUDA kernels for McCormick (an LP per
   state), vertex enumeration or product processes is new work and out of scope here.
   - A **wrong result or hang** is a correctness bug: fix it in this commit so that the call raises a clear,
     documented error (e.g. `ArgumentError` naming the unsupported algorithm/model and the CUDA backend), with a
     regression test. This is allowed by § Findings policy because it restores documented behaviour.
   - An **unclear error** (`MethodError`, scalar indexing) is replaced by the same clear error, with a test.
   - A **silent CPU fallback** that returns correct values is left as it is, but documented (docstring of the affected
     solver/model and `docs/src/` where CUDA support is described) and recorded in § 8 with its measured cost.
   - If making the behaviour explicit would change a tier 1/2 interface, stop and raise an `I-<n>` Finding instead.
3. Update the CUDA "cannot run" table in `REPORT.md` § 6.3 with the measured behaviour per case, and mark C-1 in § 8 as
   resolved (with the commit) or as "documented limitation".

Adds or semantically changes a VI/Bellman algorithm: **no**. Every change computes the same result as the merge base
within the tolerances of `common.md` § Julia Behavior & Tests; anything else is raised as a Finding (`S-<n>`) and not
merged. Tier 1/2 interface changes: only additive keywords with defaults, documented; anything wider is an `I-<n>`
Finding (`common.md` § Interface Stability). Lean: if a Julia function cited by a Lean docstring is renamed, moved or
split, update the docstring in this run and keep `lake build` and `check_julia_refs.py` green.
Follow `common.md` § Context budget. Ops: push the commit to `perf/phase-3` (same draft PR).
